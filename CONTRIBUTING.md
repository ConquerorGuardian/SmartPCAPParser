# Как участвовать в проекте

Спасибо, что заглянули. Проект небольшой, и любая помощь заметна: сообщение
об ошибке, новый протокол в словаре, правка текста справки.

## Быстрый старт

```bash
git clone https://github.com/Whitemoneydealer/SmartPCAPParser.git
cd SmartPCAPParser
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements-dev.txt
python main.py
```

Нужен Python 3.11+ (проверено на 3.13). Единственная runtime-зависимость —
`customtkinter`; всё остальное — стандартная библиотека. Это осознанное
решение: программа должна работать на машине, где ничего не установлено.

## Тесты

```bash
python -m tests.run_all        # все модули, 175+ проверок
python -m tests.test_engine    # один модуль
pytest -q                      # то же через pytest
```

Тесты — обычные функции `test_*` с `assert` и печатью `PASS:`. Раннер
`tests/run_all.py` собирает их по списку: если добавляете тест, добавьте
функцию в список `tests = [...]` своего модуля, иначе он не запустится.

Что покрыто: движок фраз, чтение pcap/pcapng, вычислитель фильтров, потоки,
статистика, вердикт, настройки, консольный режим, GUI (смоук-тесты на
реальном окне через xvfb в CI).

## Линтер и стиль

```bash
ruff check .
```

- Строки до 100 символов, комментарии и тексты интерфейса — по-русски,
  идентификаторы — по-английски.
- Никаких новых зависимостей в `requirements.txt` без веской причины.
- Парсер не должен доверять данным из файла: любые длины и смещения
  проверяются, исключения ловятся, приложение не падает на битом дампе.
- Пользовательские сообщения объясняют, что делать, а не только «ошибка».

`ruff format` проект сознательно не применяет (в истории — осмысленные
переносы), но новый код лучше держать в том же стиле.

## Сборка exe

```bash
python tools/build_exe.py --both       # один файл + папка
python tools/check_exe.py dist/SmartPCAPParser.exe dist/SmartPCAPParser/SmartPCAPParser.exe
```

Иконка перерисовывается `python tools/make_icon.py` (нужен Pillow), бэкап
проекта — `python tools/backup.py --note "..."`.

## Что можно улучшить

Порядок — от простого к сложному:

1. **Словарь.** Новый протокол — это несколько строк в
   `parser/engine.py` (`PROTOCOL_FILTERS`) и группа в `PROTOCOL_GROUPS`.
   Добавьте тест в `tests/test_engine.py`.
2. **Примеры в справке.** `gui/help_text.py` и `docs/EXAMPLES.md` — тексты,
   которые видит пользователь первыми.
3. **Фильтры.** `parser/matcher.py` — новое поле (например, `ip.dsfield`,
   `tcp.options.mss`) с тестом в `tests/test_matcher.py`.
4. **Вердикт.** `parser/verdict.py` — новые эвристики: подозрительные домены,
   сканирование портов, аномалии. Нужны тесты на синтетических дампах.
5. **Скорость.** `tools/bench.py` и профилирование на дампах 100 МБ+.

## Pull request

1. Одна задача — один PR, ветка от `main`.
2. Тесты и `ruff check .` — зелёные (CI проверит сам).
3. Если меняется поведение — обновите `CHANGELOG.md` и, если нужно,
   `README.md`/`docs/`.
4. В описании: что было, что стало, как проверить. Для UI — скриншот до/после.

Коммиты: короткая строка в повелительном наклонении на русском или
английском (`добавлен протокол mqtt`, `fix: port range filter`). Тело — по
желанию, если нужно объяснить «почему».

## Сообщить об ошибке

Приложите: шаги, ожидаемое и фактическое поведение, версию приложения
(`--version`), версию Windows, и, если можно, дамп, на котором
воспроизводится. Дампы с чувствительными данными не прикладывайте — можно
прислать только фрагмент или синтетический пример из `tests/`.

Безопасность и уязвимости — отдельно, см. [SECURITY.md](SECURITY.md).
